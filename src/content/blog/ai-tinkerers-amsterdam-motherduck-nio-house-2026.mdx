## MotherDuck: Conversational BI on DuckDB

The headline demo came from the **MotherDuck** team — **Niclas** (presenter) and **Adithya Krishnan** (co-presenter) — showing how conversational AI transforms analytics.

### DuckDB: SQLite for Analytics

The pitch is simple: DuckDB is an in-process analytical database with zero dependencies that runs anywhere. Install with `pip install duckdb`, create tables from Parquet files, and query immediately.

![DuckDB introduction — SQLite for analytics](/blog/events/ai-tinkerers-amsterdam-motherduck-8.jpg)

### What If Your Laptop Is Not Enough?

When data outgrows your laptop or you need to share databases across a team, MotherDuck extends DuckDB to the cloud. One line of code bridges local and cloud:

```python
import duckdb
duckdb.sql("ATTACH 'md:my_warehouse'")
duckdb.sql("SELECT region, SUM(revenue) AS total FROM my_warehouse.sales GROUP BY 1")
```

Results: Americas 48.3M, EMEA 31.2M, APAC 22.8M — cloud-scale data with local-speed queries.

### Agents Are the Driver

The architecture behind the magic is a 3-step MCP (Model Context Protocol) flow:

1. **Explore** — Claude runs SQL against MotherDuck databases to understand schema and shape
2. **Learn** — calls `get_dive_guide`, a dedicated tool returning the full dive API reference
3. **Create + Update** — MCP server validates the dive code, checks libraries, verifies all queries run; if something fails, it tells Claude to fix again

![Agents Are the Driver — 3-step MCP flow](/blog/events/ai-tinkerers-amsterdam-motherduck-9.jpg)

### Built for the Cloud

MotherDuck's cloud architecture provides four guarantees:

- **Hyper Tenancy** — one DuckDB per user, fully isolated, no shared state
- **Zero-Copy Clones** — branch a database instantly without copying (clone shares storage)
- **Snapshots + Time Travel** — always recoverable, rewind to any point with a single command
- **Perfect for Agents** — safe autonomous writes; give an agent its own clone, let it write freely

![Built for the Cloud — 4 architecture pillars](/blog/events/ai-tinkerers-amsterdam-motherduck-10.jpg)

### Running Untrusted Code Safely

Since dives are user-generated code (created by AI agents), they cannot run directly on the MotherDuck website. The security model:

- `app.motherduck.com` provides dive content via `postMessage`
- Code runs in a sandboxed `iframe` on `motherduck.usercontent.com`
- The iframe renders dive components and calls `useSQLQuery(...)`
- Safety: no DROP, DELETE, ALTER — queries run via DuckDB WASM only

![Running Untrusted Code — sandboxed iframe architecture](/blog/events/ai-tinkerers-amsterdam-motherduck-11.jpg)

### Validation Before Deploy

Every dive goes through three gates before it ships:

1. 🔵 **Parse and validate JavaScript** — must follow supported structure, only allowed features permitted
2. 🟢 **Validate queries are runnable** — test all SQL against the actual data
3. 🟠 **Upload to MotherDuck** — MCP server uploads the dive where it can be viewed and shared

![Validation Before Deploy — 3-gate pipeline](/blog/events/ai-tinkerers-amsterdam-motherduck-12.jpg)

### Hybrid Query Execution

The key to instant interactivity: run queries where the data lives.

- **Initial query fetches from MotherDuck** — first load pulls data from cloud, results cached locally in the browser
- **DuckDB WASM handles everything after** — full engine compiled to WebAssembly; filters, aggregations, and drill-downs execute client-side with zero latency
- **Custom SQL for smarter caching** — built SQL extensions that let the WASM engine cache results more aggressively; filter changes hit local data

![Hybrid Query Execution — cloud fetch then local WASM](/blog/events/ai-tinkerers-amsterdam-motherduck-13.jpg)

## DoneThat: Adaptive Proactive Agents

**Christoph Hartmann** demoed **DoneThat** — an AI productivity coach that decides *when* to reach out, not just responds when asked.

### The Architecture

Built on Firebase with an Electron desktop client ([open source on GitHub](https://github.com/donethatai/donethat-electron), 11 stars). The codebase shows `ACTION_RECOMMENDATION_DEFINITIONS` in TypeScript — each action has:

- A category and prompt description
- Context providers (e.g., `CTX_DOCS_AGENT`)
- Allowed surfaces (`DAILY_ONLY`)
- Evaluation functions checking analytics and live state

![DoneThat definitions.ts — action recommendation engine](/blog/events/ai-tinkerers-amsterdam-motherduck-14.jpg)

### Daily Email Summaries

The agent sends proactive daily summaries via Gmail: "How did you feel today?" with goals breakdown, task completion, and coaching nudges.

![DoneThat daily email summary in Gmail](/blog/events/ai-tinkerers-amsterdam-motherduck-15.jpg)

### Firebase Event Store

The backend uses Cloud Firestore with collections for `action_recommendation_events`, storing each proactive decision: action type, channel, delivery settings, and the full system prompt defining the AI coach persona.

![Firebase Firestore backend — event documents](/blog/events/ai-tinkerers-amsterdam-motherduck-16.jpg)

### Privacy-First Design

DoneThat takes data privacy seriously:

- **Raw data stays local** — screenshots and activity logs captured locally, processed in real time, discarded rather than stored
- **BYO LLMs** — send raw activity data to your own Gemini or OpenAI-compatible model; only structured output reaches their servers
- **Open source verification** — desktop capture layer fully inspectable on GitHub
- **Visibility controls** — slider from Private → Team → Organization → Public

![DoneThat privacy page — data flow diagram](/blog/events/ai-tinkerers-amsterdam-motherduck-18.jpg)

![DoneThat open source repo — donethat-electron](/blog/events/ai-tinkerers-amsterdam-motherduck-17.jpg)

## Demo 3: Solace Agent Mesh — Event-Driven Agent Orchestration

**Hari Rangarajan** took the stage with **Solace Agent Mesh** — an enterprise-grade multi-agent orchestration platform built on Solace's PubSub+ event broker with native **A2A (Agent-to-Agent) protocol** support.

![Hari Rangarajan presenting Solace Agent Mesh chat interface](/blog/events/ai-tinkerers-amsterdam-motherduck-22.jpg)

### The Platform

The Agent Mesh UI features six core modules: **Chat**, **Agent Mesh**, **Projects**, **Prompts**, **Activities**, and **Evaluations**. The Agent Mesh tab reveals sub-sections for Agents, Workflows (experimental), Connectors, Gateways, and Models — a complete control plane for multi-agent systems.

![Solace Agent Mesh — 8 active agents in card view](/blog/events/ai-tinkerers-amsterdam-motherduck-23.jpg)

Hari demonstrated **8 active agents** running simultaneously:

- **Acme Retail PIM Agent** — product catalog data from PostgreSQL-backed PIM
- **Bedrock Legal Agent** — compliance assistant backed by AWS Bedrock
- **Orchestrator** — manages tasks and coordinates multi-agent workflows
- **Order Exception Triage Agent** — recovery planning for delayed/broken orders
- **Quote Planning Agent** — orchestrates across PIM, SAP Joule, shipping, and legal
- **Replenishment Planner Agent** — planning using SAP, PIM, and shipping agents
- **SAP Joule RFQ Agent** — processes RFQ requests with inventory, pricing, and sourcing
- **Shipping Agent** — real-time rates, delivery estimates, and carrier options

### The Demo: End-to-End RFQ Processing

The killer demo: an inbound email from `operations@alpine-energy.eu` requesting a quote for **200 flow meters** (SKU MAT-500200) and **200 gasket sets** (SKU MAT-700200), delivered FCA to Lacchiarella (MI), Italy by 2026-10-30.

![Solace Agent Mesh — RFQ orchestration flow with parallel agent execution](/blog/events/ai-tinkerers-amsterdam-motherduck-24.jpg)

The orchestrator enforced strict rules:
- Validate every SKU against AcmeRetailPim before pricing
- If discontinued, propose one compatible substitute with rationale
- Use real SAP sourcing/availability and real ShippingAgent costs — no invented values
- Final response must include JSON output, per-line evidence sources, and a risk register

![Solace Activities view — full event trace with topic paths and timestamps](/blog/events/ai-tinkerers-amsterdam-motherduck-28.jpg)

The **Activities** view exposed the full event trace — Solace topic paths (`solace-agent-mesh/v2/v1/gateway/status/...`), STATUS-UPDATE messages from OrchestratorAgent, and LLM invocations using `openai/bedrock-claude-4-5-haiku`.

![Solace Agent Mesh — orchestrator delegating to QuotePlanningAgent with task arguments](/blog/events/ai-tinkerers-amsterdam-motherduck-29.jpg)

The delegation chain was fully observable: Orchestrator analyzing the RFQ → delegating to QuotePlanningAgent with explicit task arguments → parallel fan-out to PIM Agent (`execute_sql_query`), SAP Joule Agent (`run_mock_joule_asse...`), and Shipping Agent.

### Why It Matters

Solace's approach to agent orchestration is fundamentally different from chain-of-thought frameworks:

1. **Event-driven, not polling** — agents communicate via PubSub+ topics, enabling true async parallelism
2. **A2A protocol support** — Google's open standard for agent discovery and task delegation
3. **Full observability** — every LLM call, tool invocation, and status update is traced with timestamps and topic paths
4. **Enterprise integration** — native connectors to SAP, PostgreSQL, AWS Bedrock, and custom gateways
5. **Artifact generation** — the final JSON output (3.17 KB) is a downloadable, auditable quote document

## Key Takeaways

1. **Conversational BI is production-ready** — MotherDuck's MCP + DuckDB WASM + Claude pipeline generates shareable, interactive dashboards from natural language
2. **Agent safety requires architecture** — sandboxed iframes, validation gates, and read-only WASM execution keep AI-generated code safe
3. **Proactive beats reactive** — DoneThat's approach of deciding *when* to engage (vs. waiting for prompts) is the next frontier for personal AI
4. **Privacy and AI can coexist** — BYO LLM, local processing, and open source capture layers prove you do not need to sacrifice data control for intelligence
5. **Event-driven agent orchestration scales** — Solace proves that PubSub+ messaging patterns beat sequential chains for multi-agent enterprise workflows
