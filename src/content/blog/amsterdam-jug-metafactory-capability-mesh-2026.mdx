## From service mesh to capability mesh

In the microservices era, the hard problem was the network: service discovery, retries, mTLS, traffic shaping. We solved it with the **service mesh**.

In the agentic era, the abstract says, the integration problem is about **capabilities**, not networking. An orchestrator does not call `POST /orders`. It decides *"I need something that can look up an order"* and picks an agent or tool that offers that capability.

And the old problems come back in a new form:

- **Discoverability:** how does the orchestrator find the right capability?
- **Scalability:** what happens with hundreds of tools in the context window?
- **Observability:** which agent did what, and why?
- **Explainability and unintended actions:** LLMs are non-deterministic, so "it worked yesterday" is not a guarantee.

The proposal: move from **technical service contracts** to **semantic capability integration**.

## The five topics

The talk is organised around five ideas:

1. **From OpenAPI to MCP: the protocol shift.** OpenAPI describes endpoints for developers. MCP describes tools for models: a name, a natural-language description, and a typed input schema that a model can read and choose from.
2. **Capability hierarchies: composing agents at scale.** Small capabilities compose into bigger ones, and the orchestrator reasons at the right level instead of seeing a flat list of hundreds of tools.
3. **Human-on-the-loop.** The human moves from approving every step (in the loop) to supervising and setting boundaries (on the loop).
4. **Policy as code.** Governance for autonomous agents written as versioned, testable rules, like we already do for Kubernetes admission control. (If you know OPA or Kyverno, this will feel familiar.)
5. **Observability and safety: tracing agent behaviour.** Every capability call is traced, so you can explain afterwards what the system did.

## The demo repository

The repo is a deliberately small mesh, so the architecture is easy to see. It is a Maven multi-module project (Java 25, Spring Boot 4.1.1, Spring AI 2.0.1). Each module is an independent Spring Boot app, and most expose a remote MCP server over the **Streamable HTTP** transport:

| Module | Capability | Port |
|---|---|---|
| `echo-printer` | `echo`: returns the letter or digit it is given | 8081 |
| `char-printer` | 26 no-input tools, `a` to `z`, returning the uppercase letter | 8082 |
| `second-character-printer` | `second_character`: second character of a string | 8083 |
| `random-printer` | `random_character`: a random character from a 6-character string | 8084 |
| `next-char-printer` | `next_character`: next letter of the alphabet, `Z` wraps to `A` | 8085 |
| `mcp-registry` | REST API to **discover** the servers above | 8090 |

The printers are toy capabilities on purpose. What matters is the shape:

- **Tools are plain annotated methods.** In Spring AI you expose a capability with `@McpTool`, and the starter `spring-ai-starter-mcp-server-webmvc` does the rest. Adding a new server means a new module, a port, a server name and one annotation.
- **Discovery is a registry, not a config file.** `mcp-registry` implements the read endpoints of the MCP [generic registry API](https://github.com/modelcontextprotocol/registry) (`GET /v0.1/servers`, with search and pagination), seeded with the five servers. A client asks the registry what exists and then connects to the right MCP server.
- **A real-world detail.** Server names are reverse-DNS with a slash, like `nl.makan1869.capabilitymesh/echo-printer`, and the spec requires `%2F` in the URL. Tomcat rejects that by default, so the registry reconfigures the connector to pass it through, with an integration test that sends real encoded requests. The kind of thing you only learn by building it.
- **Strict inputs.** `echo-printer` accepts only a letter or a digit. Tool input is untrusted: the model fills in the parameters.
- **One image to try it all.** `./build/build.sh` builds all six jars into a single Docker image with all ports exposed.

There is also a `capability-mesh-agent-card` module, an agent in action derived from the Spring AI community skills demo.

## Why this matters for platform teams

If you run a platform, you know the next question: *who owns the catalogue of capabilities, and who decides which agent may call which?* A registry plus policy as code plus traces is the same pattern as a service catalogue plus admission control plus OpenTelemetry. The vocabulary changed. The discipline did not.

For the identity and permission side of the same problem, see my post on the [8-layer stack of an enterprise AI assistant](/blog/enterprise-ai-assistant-8-layer-stack-2026/), and the earlier Amsterdam JUG talk on [legacy Java services as MCP tools](/blog/amsterdam-jug-graphql-mcp-2026/).

## Try it yourself

```bash
git clone https://github.com/makan1869/capability-mesh
cd capability-mesh
mvn clean verify
mvn -pl mcp-registry spring-boot:run
curl "http://localhost:8090/v0.1/servers?limit=2"
```
