The middle talk of the Amsterdam JUG evening at **Metafactory** was *"Capability Mesh: Architecture for the Agentic Era"* by **Makan Sepehrifar**, staff engineer at **Productboard**. He opened with a warning: the first fifteen minutes would be theory, because he needed it for the rest. It was worth it. And then he printed the letters A, B and C in the most over-engineered way I have ever seen, on purpose. The code is public: [makan1869/capability-mesh](https://github.com/makan1869/capability-mesh).

Makan has spent the last months building **AI pull-request reviewers** at Productboard. Before that, he was a solution architect at a consultancy, which is where the architecture patterns in this talk come from.

## What is an agent, anyway?

His definition: an agent is an **autonomous, goal-oriented computational system**. The programming language and the stack do not matter, and a human can be an agent too. An **AI agent** is the same thing, but it uses an AI model to reach its goal: inputs, a reusable prompt (the system instructions), a large language model, an output.

A **multi-agent system** has three parts: a **dispatcher** that splits the input into manageable tasks, **agents** that each handle a task, and an **aggregator** that combines the results. Adding AI changes each part:

- the dispatcher understands **natural language** and detects intent;
- some deterministic agents become **AI agents**;
- the **shared context** can be natural language, instead of a state machine or a structured knowledge board;
- **agent selection** can be autonomous: give the dispatcher a list of agents and let it choose;
- the aggregator can **summarise** the result in natural language.

## Why many agents instead of one big one

Makan gave four reasons:

1. **Noise reduction.** The *lost in the middle* effect: as a single agent's context grows, what is in the middle of it gets lost, and precision drops.
2. **Context purity.** Each agent gets a small context that is exclusive to its task. (The same idea as smaller specs in the talk before.)
3. **Control, monitoring and observability.** With one agent you see input and output. With several, every hand-off is a point where you can see what is passed and what is selected.
4. **Predictability and integration.** You can combine **deterministic** agents with non-deterministic ones.

## What "scalable" means for agents

The real question of the talk was not *how do agents talk to each other*, but **how do you build a scalable agent architecture**. His requirements:

- many agents, and **many instances of the same agent**;
- **isolated execution**, horizontal scaling, **stateless** agents;
- **intent-based routing**: select an agent by the goal you want to reach;
- **dynamic replacement**: if one agent goes down, another takes over;
- **state aggregation**: state lives in a resilient aggregator, not in the agents.

## Same problem, different decade: the service mesh

Around 2010, microservices raised the same questions: how do services find and call each other, and how do you scale them? The answer was the **service mesh** with a **service registry**: ask for "an instance of the flight service" and you get one, wherever it runs, as long as it is up and answers under that name.

A **capability mesh** applies that to agents:

1. Agents are grouped by **capability, not by name**. Not "the flight service", but any agent that can *book a flight*, *search flights* or *search a geolocation*.
2. A **unified integration protocol**, so one agent can be swapped for another.
3. The agent's execution is **encapsulated** in the capability. You care about inputs and outputs, not how it does the work.
4. The execution flow is **managed, or at least audited**.

His example: the aggregator asks *"is there any agent that can search for events in Europe?"*, one answers *"I can"*, and the request *"find me the top developer community event"* comes back with *"Amsterdam JUG, November."* How that agent found it does not matter.

## The protocol: MCP or A2A

There are two well-known options, and the difference is **what you pass**:

| | MCP (Model Context Protocol) | A2A (Agent2Agent) |
|---|---|---|
| Style | Remote procedure call | Agent-to-agent delegation |
| You pass | **Parameters** for a tool | A **goal** or purpose |
| The other side | Any agent, AI or not | Needs an AI agent to interpret the goal |

## Discovery: registries and agent cards

Communication is only half of it. You also need **discovery**:

- **MCP** has an official [MCP Registry](https://github.com/modelcontextprotocol/registry). Each entry is a server with a name and a description (his example was a server that searches available hotels by city or by coordinates), and each server exposes typed tools. The official registry API was frozen at **v0.1** in October 2025, and v0.1 is also the version Makan's own registry implements.
- **A2A** has community registries where every agent **publishes its agent card**, a description of its identity and skills, into a pool of agents.

Makan wrote his own MCP registry for the demo. The difference with the official one: his is **transient** and it **health-checks** the servers, so only servers that are up are offered.

## The demo: printing "ABC" the hard way

The demo started with an **empty registry** and a Spring AI client with one instruction: *you are a printer, print the text the user gives you, and call exactly one tool per character.* Then he added MCP servers one by one:

1. **echo-printer** (returns the letter or digit you give it). Target `ABC`: the model called `echo` three times.
2. **char-printer** (26 tools, `a` to `z`, no input). Same target, and the model **switched** to the dedicated `a`, `b`, `c` tools. Two unrelated servers, which could run on different continents, offered the same capability. That is the interchangeability a capability mesh is about.
3. **next-char-printer** (returns the next letter). Nothing changed: the model had better options.
4. **second-character-printer** (returns the second character of any string, with no character restrictions). He changed the target to `ABC02`, and the model started **combining four different servers** to build it.
5. **random-printer** (a random character from a six-character string). It can produce anything, including symbols, but only by chance. With a `+` in the target, the model used `second_character` instead (call it with `A+` and you get `+`) and almost never picked the random printer: as Makan said, that would be very unreasonable, *"but sometimes it does."*

A last variant printed the model's **reasoning**, so you could see *why* it chose `second_character` for the `+`. The result: an MCP registry plus an MCP client, horizontally scalable (add as many servers as you want), with **stateless agents** and all state in the aggregator. And, in his words, a very, very costly way of printing ABC.

## Three kinds of orchestrator

Makan separated orchestrators into three kinds:

1. **Workflow managers**: deterministic workflows with integrations to all sorts of protocols.
2. **Workflows with agentic capabilities**: they can call agents, but the workflow itself is still deterministic.
3. **AI orchestrators**: what he showed. The workflow is **built at runtime** from the tools that happen to be available. Change the set of tools, and the workflow changes. Only the goal is fixed.

## Humans are agents too

Because an agent is anything autonomous and goal-oriented, a **human** fits in the same architecture. A step can be delegated to a person, or a confirmation can be requested through an MCP client: if the first approver is not available, ask the next one. Human-in-the-loop, or on-the-loop, becomes one more capability in the mesh.

## In production: AI code review at Productboard

His real use case: **pull-request review**, split into dimensions such as **architecture, security and consistency**, each handled by its own agent. They run on **multiple models through MCP**, and they are interchangeable: if a model is not available or too expensive, another one takes the dimension.

His closing warning was the same one as in the demo: calling MCP servers for everything is a **very costly way** of doing AI. Use the pattern where you need the scale and the interchangeability, not by default.

## The repository: two layers of capability

The [repo](https://github.com/makan1869/capability-mesh) is a Maven multi-module project (Java 25, Spring Boot 4.1.1, Spring AI 2.0.1) with **eight modules** (the README lists six).

**Layer 1, tools (what the demo showed).** Five MCP servers over Streamable HTTP, a registry, and the `printer` client:

| Module | Capability | Port |
|---|---|---|
| `echo-printer` | `echo`: the letter or digit you give it (a-z, A-Z, 0-9) | 8081 |
| `char-printer` | 26 no-input tools, `a` to `z`, each returning the uppercase letter | 8082 |
| `second-character-printer` | `second_character`: the second character of any string | 8083 |
| `random-printer` | `random_character`: a random character from a 6-character string | 8084 |
| `next-char-printer` | `next_character`: next letter, `Z` wraps to `A` | 8085 |
| `mcp-registry` | Read-only MCP registry API (`GET /v0.1/servers`) | 8090 |

Tools are plain methods with Spring AI's `@McpTool`. In the public version, the registry is **seeded from `server.json` files**, and it handles a detail you only learn by building it: server names contain a slash, the spec requires `%2F` in the URL, and Tomcat rejects that by default. The `printer` client uses the task `Print ABC02+`, and its system instructions deliberately do not say which tool prints which character, so the model has to reason from the tool descriptions.

**Layer 2, agents (in the repo, not shown on stage).** The `capability-mesh-agent-card` module wraps printers as agents with a small hand-written **A2A-style** API: `GET` returns an **agent card** (name, description, URL, version, skills with tags and examples), and `POST` accepts a **JSON-RPC 2.0** task. One agent asks an LLM to produce its letter (non-deterministic inside), and a "smart" agent prints any letter. A **smart orchestrator** fetches every agent card, asks the LLM for an ordered plan as **structured output** (*which agent, which letter*), preferring dedicated agents, and then plain code calls only those agents. **The model plans, the code acts.** Note that the demo uses `tasks/send`, the method name from early A2A versions; the current A2A specification uses `message/send`.

API keys come from the `ANTHROPIC_API_KEY` environment variable, and the repo has no licence file at the time of writing: read it and learn from it, but ask the author before reusing code.

## My takeaways

- **Name capabilities, not services.** An orchestrator that asks *"who can do X?"* survives model changes, outages and new vendors. One that calls *"service Y"* does not.
- **Descriptions are the new API contract.** In the demo, the model's choices came entirely from tool descriptions. Write them like you write an OpenAPI spec: precise, honest about limits.
- **Keep state out of agents.** Stateless agents plus a resilient aggregator is what makes replacement and scaling possible.
- **Watch the cost.** Every hop through a model costs money. A mesh is for when you need interchangeability at scale.

If you run a platform, the next question is familiar: *who owns the catalogue of capabilities, and who decides which agent may call which?* A registry plus policy plus traces is the service catalogue, admission control and OpenTelemetry pattern again. For the identity and permission side, see the [8-layer stack of an enterprise AI assistant](/blog/enterprise-ai-assistant-8-layer-stack-2026/), and the earlier Amsterdam JUG talk on [legacy Java services as MCP tools](/blog/amsterdam-jug-graphql-mcp-2026/).

## Try it yourself

The mesh needs Java 25 and Maven; the clients also need an Anthropic API key in `ANTHROPIC_API_KEY`.

```bash
git clone https://github.com/makan1869/capability-mesh
cd capability-mesh
mvn clean verify

# the registry (port 8090)
mvn -pl mcp-registry spring-boot:run
curl "http://localhost:8090/v0.1/servers?limit=2"

# each MCP server in its own terminal, for example:
mvn -pl echo-printer spring-boot:run
```

Or run `./build/build.sh` to put all six servers in one Docker image, then start the `printer` module and watch the model discover the tools.
