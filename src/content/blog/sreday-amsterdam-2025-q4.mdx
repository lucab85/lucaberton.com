[SREday Amsterdam 2025 Q4](https://sreday.com/2025-amsterdam-q4/) took place on 7 November 2025, with the official agenda listing ING Cedar as the venue and two tracks. This post covers the five main-room talks I have recordings of. Speakers are named as in the official agenda; where I only have the agenda and the recording to go on, I say so. I covered the event briefly in my [Amsterdam AI meetups roundup](/blog/amsterdam-ai-meetups-autumn-2025-roundup/); this post goes deeper on the talks.

![The SREday main stage before the first talks, with an SRE DAY banner, a Reliability Guild banner and an empty speaker table](/blog/events/sreday-amsterdam-2025-q4/main-stage-before-talks.jpg)

*The main stage before the talks started.*

## What Observability Can Learn From BI (Imply)

The 10:00 keynote on the agenda was **Peter Marshall** (Imply), "What Observability Can Learn From BI: Decoupling for Speed, Scale, and Flexibility". The slide I photographed matches the recording: four principles, **Data is a shared asset**, **Ease of use**, **Technology independence** and **Interoperability**, with a Kafka slide under the first one.

![The audience at SREday watching a keynote slide titled Data is a shared asset, with the Kafka logo and three bullets about a buffer and transport layer, a persistent replayable log and a shared interface across producers and consumers](/blog/events/sreday-amsterdam-2025-q4/keynote-kafka-slide-scene.jpg)

*The keynote slide on Kafka as an example of a shared data layer.*

![Close-up of the slide: Data is a shared asset, Kafka as a buffer and transport layer, a persistent replayable log, and a shared interface across producers and consumers](/blog/events/sreday-amsterdam-2025-q4/data-is-a-shared-asset-kafka-slide.jpg)

*Kafka does not care whether a record is a metric or a log, which was the point of the slide.*

The argument, as I heard it:

- **Shared data.** Teams use the same data for different jobs, so you should not build duplicated pipelines just because one signal is called a metric and another a log. The speaker's example was Kafka, which treats both the same.
- **Ease of use and open formats.** The speaker asked vendors to stop inventing a new query language and UI for every backend, and pointed to a talk from KubeCon London on the topic.
- **Independence through decoupling.** The speaker drew a parallel with the move from the closed Hadoop stack to open table formats such as Iceberg, with separate storage and query engines. For observability he proposed three boxes: telemetry collection (collect openly, with OpenTelemetry), information management (store responsibly) and insight generation (the UI).
- **The pitch.** The middle box is where Imply plays, with a product called **Lumi**, which the speaker described as a warehouse for observability data. According to the speaker, it can look like a Splunk forwarder target, answer LogQL from Grafana or SQL from Tableau over JDBC, and ships an MCP server. The speaker claimed about three times better compression than their previous tool, and said the performance figures came from developer relations, not marketing. Treat vendor numbers as vendor numbers; the [Imply announcement](https://www.businesswire.com/news/home/20250908960771/en/Imply-Launches-Imply-Lumi-The-Industrys-First-Observability-Warehouse) describes Lumi as an observability warehouse.

My take: the three-box model is a useful way to review your own stack. If your collector, storage and UI come from one vendor, ask which of the three you could swap without a migration project. OpenTelemetry already gives you the first box; the second is where most lock-in sits.

## How ClickHouse built ClickStack

At 14:00 **Dale McDiarmid** (ClickHouse) presented "How We Built ClickStack - an open source, open telemetry native Observability stack". ClickHouse's [ClickStack documentation](https://clickhouse.com/docs/use-cases/observability/clickstack/overview) describes three components: ClickHouse as the database, the HyperDX UI, and an OpenTelemetry Collector for ingestion.

The parts of the recording I could use clearly:

- The speaker introduced ClickHouse as an open-source column-oriented OLAP database, "designed for analytical data" in contrast to a transactional database like Postgres, and framed observability as just another analytics use case. He said the stack became part of ClickHouse in April 2025, while the design decisions were taken before that, by a separate team.
- Getting started is one Docker command, and there is a public demo you can query. The speaker described a public data set of about half a billion rows.
- On licensing, the speaker said the UI is MIT-licensed and the database Apache 2.
- **Q: What about RBAC?** The database layer has it, but today every user connects with their own credentials. Reflecting database permissions in the UI was, in his words, probably the biggest internal task at that moment.
- **Q: Why not build the UI inside Grafana?** It was considered; the speaker said the licence was not friendly to them. Many people still use Grafana against ClickHouse when they need to correlate other data stores.
- **Q: Would SQL work as a common query language for observability?** The speaker had no strong opinion and thought SQL is a good base to build interfaces on, but not the natural language for SREs until they do deep analysis.

A large part of this recording came out garbled, so I am not summarising the design-decision section (columnar storage, schema handling, object storage) beyond what the docs say.

## Private cloud AI platform engineering (Coté)

At 14:30 the main stage showed **Coté**'s title slide: "Private Cloud AI Platform Engineering: What little we right know now, maybe". The agenda lists **Michael Cote** (Tanzu) with a different title, "Platform Engineering and AI - Two Buzzwords Finally Meet!", so I use the title on the slide. My photo of that slide is in the [autumn roundup](/blog/amsterdam-ai-meetups-autumn-2025-roundup/#sreday-amsterdam-2025-q4-7-november).

The recording of this talk has long stretches where the transcript looped, so I only have the first part:

- A survey slide showed security at the top, as always, but the speaker's reading was that the bulk of priorities were the old ones: modernisation, maintenance, keeping things running. His half-joking advice was that simply upgrading your stack could be the most valuable thing for the next 12 months, "but in the meantime, why not some AI".
- A list of what platform teams will probably own for AI: hosting models (inference), application frameworks, registries for plugins (the speaker named MCP and agent skills), and cost control, monitoring and observability, including AI FinOps.
- A split of roles. Developers build applications on the models they can access, the platform team runs the service, and it is still open who chooses and updates models: operations or a "data scientist"-type role.
- Why private cloud: the speaker said that from surveys and conversations, many organisations want control over how AI is used, not just developers calling public services directly.

My take: the registry and cost-control items are the new work. Hosting a model is just another workload; deciding which plugin or tool an agent may call, and who pays for the tokens, is where platform teams need a policy.

## Securing MCP servers with API Management

The 15:00 agenda slot was **Alessandro Vozza** (Microsoft), "The USB-c for your Copilot: Securing MCP Servers with API Management". I did not photograph his slides. I match the recording to the talk by the timestamp, by the speaker saying he works at Microsoft, and because a later speaker referred to "Alexandro" and API Management.

What the talk covered:

- **What an agent is.** An LLM plus tools and memory, able to write files, push to GitHub or run commands. The speaker's line was that agents will not replace software because agents are software.
- **Why MCP.** Models cannot reach live data on their own, and everyone was building bespoke integrations. The [Model Context Protocol](https://modelcontextprotocol.io) came from Anthropic as an open specification, which the speaker compared to USB-C. Under the hood it is JSON-RPC over HTTP, with server-sent events as the older transport and streamable HTTP as the newer one.
- **Tools, resources, prompts.** MCP servers expose all three, but tools are the part that matters in practice. The speaker advised keeping tool descriptions short, because the model reads them to decide what to call.
- **Pattern, not a product.** Security grows with adoption: "like a YOLO" is fine for a hobby project, but not for a bank. He showed Azure API Management in front of an MCP server he wrote in Go, with a subscription key, private endpoints and a JSON payload visible in the gateway.
- **Demo.** The server had a couple of toy tools (add two numbers, return a joke), tested with the MCP Inspector and then from the Copilot CLI. The last call from the CLI failed on stage, and the speaker took it with good humour.

He also mentioned the MCP registry idea, comparing it to Docker registries, and the Dutch Cloud Native and AI meetup community.

My take: putting MCP behind a gateway is the same lesson as with every other API. Authentication, rate limits and audit belong in one place, not in each server.

## Securing cloud automation on Azure

The last talk I recorded was in the 17:30 slot, **Leo Visser** (OGD ict-diensten), "Secure your cloud automation". The recording fits the title, and the speaker referred to the earlier API Management talk. He walked through two Azure options:

- **Automation accounts with runbooks.** Cheap and good for background work. He had seen runbooks calling runbooks, with users pressing a button, getting coffee, and coming back to find the portal still blocked.
- **Azure Functions.** More control, CI/CD, many triggers. He used a consumption-plan function app, which is billed only when it runs, with the downside of a cold start. An HTTP-triggered function has a function key, which he described as effectively an API key; he preferred not to leave that key in the URL.
- **The fix: API Management in front.** It can link to the function app with a short wizard, and a JWT validation policy returns 401 without a bearer token and can check claims. See the [validate-jwt policy reference](https://learn.microsoft.com/en-us/azure/api-management/validate-jwt-policy). In his demo the call without headers failed with 401, and with a token it returned the hello-world response.

His closing advice was practical: no tool is perfect, so match it to the job; monitor and log, because every automation fails eventually; make runs retryable and re-runnable; and do not be afraid to combine systems instead of forcing everything into one function. A script on a management server that runs once a month "doesn't always have to be fancy".

## Wrapping up

Three threads ran through the talks I heard: keep telemetry open and decoupled, expect AI to land on the platform team, and put authentication in front of anything an agent or a webhook can call. The agenda had two tracks and many more talks than these five, so this is a partial picture.
