Two database evenings in Amsterdam, eight days apart, ended up fitting together well. On Wednesday **26 November 2025** I went to a meetup with AWS, PingCAP and Bolt, held in an AWS meeting space (the security posters on the wall carried Amazon branding). It covered TiDB's vector index and full-text search, and then Bolt's talk **"Building Bolt with TiDB"**. On Thursday **4 December 2025** I went to another database meetup in the city centre. The first talk there was a clear walk through concurrency anomalies and the four usual ways databases deal with them.

This is a throwback built from my photos. The talk content below comes from the slides. Where I add background, I've checked it against the [TiDB docs](https://docs.pingcap.com/) and the [PostgreSQL docs](https://www.postgresql.org/docs/current/transaction-iso.html) and link to them.

## Vector index in TiDB

The first technical slide was **"Vector Index in TiDB"**. The index uses **HNSW** (Hierarchical Navigable Small World). It needs a cluster with **TiFlash nodes**, and TiFlash has to be active for the table. The example DDL declared the index inline:

```sql
CREATE TABLE foo (
    id        INT PRIMARY KEY,
    embedding VECTOR(5),
    VECTOR INDEX idx_embedding ((VEC_COSINE_DISTANCE(embedding)))
);
```

![The Vector Index in TiDB slide: this uses HNSW, requires a cluster with TiFlash nodes and TiFlash active for the table, with a CREATE TABLE example declaring a VECTOR INDEX on VEC_COSINE_DISTANCE(embedding)](/blog/events/tidb-aws-bolt-meetup-amsterdam-2025/tidb-vector-index-hnsw.jpg)

*The vector index slide: HNSW, built on TiFlash.*

The [vector search index docs](https://docs.pingcap.com/tidb/stable/vector-search-index/) say the same thing and add a few limits worth knowing before you design a schema. HNSW is currently the only supported algorithm. TiFlash nodes have to be deployed in advance. You must specify a distance function when you create the index, and only `VEC_COSINE_DISTANCE()` and `VEC_L2_DISTANCE()` are supported. You can also add the index to an existing table with `CREATE VECTOR INDEX … USING HNSW` or `ALTER TABLE … ADD VECTOR INDEX`.

**My take:** having the index live on the columnar TiFlash replicas, not the row store, is a sensible split. Vector scans are analytical-shaped work. Keeping them off TiKV protects the transactional path that your application's writes depend on. It does mean that "add vector search" is also a capacity-planning conversation about TiFlash.

## Full-text and hybrid search

Next came **"Fulltext search"**. According to the slide, it was already available in select TiDB Cloud Serverless regions and would be released more widely. It allows **hybrid search**: a user query goes to vector search for semantic similarity and to full-text search for keyword relevance, each returns its top K, and a **reranker** merges them into a final top K.

![The Fulltext search slide: already available on select TiDB Cloud Serverless regions, will be released more widely, allows hybrid search, with a diagram of a user query going to vector search and full-text search, then a reranker](/blog/events/tidb-aws-bolt-meetup-amsterdam-2025/tidb-fulltext-hybrid-search.jpg)

*Hybrid search: vector and keyword retrieval, merged by a reranker.*

The current [full-text search guide](https://docs.pingcap.com/tidbcloud/vector-search-full-text-search-sql/) still describes the feature as early-stage and limited to certain TiDB Cloud tiers and regions. It also mentions a multilingual parser that handles English, Chinese, Japanese and Korean in the same table. I've compared a similar feature on another engine in [ClickHouse full-text search with the text index](/blog/clickhouse-full-text-search-text-index/).

The TiDB part ended with **"Try it for yourself!"** and a link to [TiDB Labs](https://labs.tidb.io). The labs on the slide included building simple vector search applications in a Jupyter notebook, RAG and Text2SQL apps with OpenAI or Amazon Bedrock, and using TiDB as unified storage for AI apps.

## Building Bolt with TiDB

The second half belonged to Bolt. The title slide read **"Building Bolt with TiDB: How Bolt Serves Millions of Customers Globally with TiDB"**, by **Leandro Morgado, Senior DBRE**, dated Amsterdam, 2025.11.26.

My photos only cover a small part of the talk: the title, one technical slide and the Q&A. That technical slide is worth looking at closely. It was about the **TiKV MVCC In-Memory Engine (IME)**:

- **When to enable it?** With a long `tidb_gc_life_time` (hours), with workloads that have many updates and deletes (for example, queues), and bearing in mind that it **only speeds up reads**.
- **How to spot it in `EXPLAIN`:** `total_keys` (versions scanned) much greater than `total_process_keys` (versions processed). The example `scan_detail` on the slide showed `total_process_keys: 10` against `total_keys: 35231`.

![Leandro Morgado presenting the TiKV MVCC In-Memory Engine slide: when to enable it, long tidb_gc_life_time, workloads with many updates and deletes such as queues, only speeds up reads, and EXPLAIN total_keys versus total_process_keys](/blog/events/tidb-aws-bolt-meetup-amsterdam-2025/tikv-mvcc-in-memory-engine.jpg)

*Bolt's slide on when the TiKV in-memory engine helps: about 35,000 versions scanned to process 10 keys.*

The [TiKV MVCC In-Memory Engine docs](https://docs.pingcap.com/tidb/stable/tikv-in-memory-engine/) match the slide. IME speeds up queries that have to scan a large number of MVCC historical versions, meaning `total_keys` is much greater than the processed keys. The docs give the same two scenarios: frequently updated or deleted records, and a longer `tidb_gc_life_time`. Their FAQ also says plainly that it only speeds up read requests that scan many MVCC versions.

**My take:** this is the kind of slide I find most useful from a production team. A queue table in an MVCC database builds up dead versions faster than garbage collection removes them. The query plan looks fine, but the scan detail tells a different story. Comparing "versions scanned" with "versions processed" is a check you can run against your own slow query log tomorrow, on TiDB or anything else built on MVCC.

## 4 December: concurrency anomalies, from dirty writes to SSI

Eight days later I was at another database meetup in central Amsterdam. My photos don't show who organised it, so I'll stick to the talks. The talks I saw covered concurrency anomalies, TiDB schema changes and ClickHouse internals. The first was by **José María Muñoz Rey, Backend Engineer** (as on his closing slide). It walked through concurrency problems using one running example: an `Events` table with a row for "Best Concert Ever", where `tickets_sold` is 9 and `max_tickets_to_sell` is 10. There's one ticket left and two buyers.

### The anomalies

**Dirty write.** A and B both buy the last ticket. A assigns the ticket to itself, B assigns it to itself and overwrites A, and then both update the counter from 9 to 10. Both buyers get a confirmation, but the ticket ends up belonging to B. Then the slide asked: "And what about the tickets_sold counter?"

**Lost update.** A reads 9, B reads 9, and both write 9 + 1 = 10. Two tickets are sold, but the counter only goes up by one.

### The solutions

The talk then covered the solutions, each with the database it's most associated with:

- **Multi-version concurrency control (MVCC)**, shown with the PostgreSQL elephant. It implements snapshot isolation / repeatable reads. A transaction only sees data from older transactions, transactions get incremental transaction IDs, and each row records the transaction that changed it. Useful against dirty reads and read skew.
- **Two-phase locking (2PL)**, shown with the MySQL and SQL Server logos. This is pessimistic concurrency: locks manage data access, in shared mode (reads can share) and exclusive mode (writes can't). Performance is "bad in general, but useful for high concurrency in a single object". Useful against dirty writes and write skew.
- **Serializable snapshot isolation (SSI)**, shown with the PostgreSQL elephant again. This is optimistic: it waits until the operation completes and then checks for conflicts, detecting writes to rows that were read earlier ("soft locks over data range"). Good for many transactions that don't touch the same data, bad for low cardinality combined with slow transactions, and "useful for every problem".
- **Atomic write operations**, the first item on the summary slide.

![The Multi-version concurrency control slide with the PostgreSQL elephant: implements snapshot isolation or repeatable reads, a transaction only sees data from older transactions, incremental transaction IDs, useful for dirty reads and read skew](/blog/events/tidb-aws-bolt-meetup-amsterdam-2025/mvcc-postgres-slide.jpg)

*MVCC, with PostgreSQL as the example.*

*The four options on one slide.*

The [PostgreSQL transaction isolation docs](https://www.postgresql.org/docs/current/transaction-iso.html) are the best companion to this talk. They confirm that PostgreSQL's Repeatable Read is implemented as snapshot isolation and its Serializable level as Serializable Snapshot Isolation. They also explain that you can request all four standard isolation levels, but only three are actually implemented, because Read Uncommitted behaves like Read Committed. That matters for the lost-update example. Under Repeatable Read, if a concurrent transaction has already committed an update to the same row, PostgreSQL rolls the second transaction back with `could not serialize access due to concurrent update`. It doesn't silently overwrite. Your application has to catch that and retry.

**My take:** the slide labels are a simplification, and that's fine for a meetup talk. MySQL's InnoDB is also a [multi-version storage engine](https://dev.mysql.com/doc/refman/8.4/en/innodb-multi-versioning.html), so the 2PL logo really refers to how it handles locking reads and writes. For the ticket example in practice, I'd reach for the cheapest fix first: an atomic `UPDATE events SET tickets_sold = tickets_sold + 1 WHERE id = 1 AND tickets_sold < max_tickets_to_sell`, then check the affected row count. Use SSI or explicit locks when the invariant spans more than one row.

### TiDB architecture and online DDL

The second talk of the evening was about schema changes in TiDB. My photos only show its closing slide, which credited **"Online, Asynchronous Schema Change in F1"** by Google as the inspiration (StateNone → DeleteOnly → WriteOnly…), and pointed to TiDB's original DDL design doc, github.com/pingcap/tidb and TiDBCloud.com. The speaker wasn't named on any slide I photographed, so I'm leaving the name out. My notes on the rest come from the clips I filmed of the talk, which only cover the middle and the end.

The speaker started with a short architecture tour. According to him, TiDB was designed as an OLTP database with some lighter analytics, and it has three node types. The SQL layer looks like a MySQL server to clients, but the protocol, parser and optimizer are re-implemented and the nodes are stateless, so they are quick to add or remove. The data lives in a row store built on an LSM tree (RocksDB) and replicated with Raft, three copies by default. Per table you can optionally ask for copies in a column store too. It is fed by the same Raft stream and carries the transaction timestamp, so both stores show the same state of the database. In his words the optimizer can mix row and column access in one query, and would pick the column store for a big single-column scan and the row store for an index lookup. The third component is the placement driver. It hands out the timestamps behind TiDB's MVCC, splits data into ranges and moves them around when it sees an imbalance in size or in read and write load, while keeping copies in different availability zones.

On DDL, he explained why a distributed database wants non-blocking schema changes. The idea is the same as a rolling application deployment: instead of stopping everything, you version the schema globally and move through intermediate states that are compatible with the previous one, so running transactions carry on. Adding an index is the textbook example:

- **None**: the index doesn't exist.
- **Delete only**: the index is not visible for reads, but deletes (and the delete half of updates) reach it. He said this state exists because a node one state behind could otherwise leave orphaned index entries.
- **Write only**: new writes go into the index, but nothing reads from it. He joked that the name is not ideal, because it also deletes, and that naming is hard.
- **Write reorganisation**: the existing rows are read and the index is backfilled. On a big table this is where most of the time goes.
- **Public**: the index is ready for queries.

Then came the practical part, which I found the most interesting. According to him, TiDB's first backfill used many small transactions: very stable and well tested, but slower than competing databases, because each transaction has its own overhead. The newer approach reads everything, sorts it and writes the result straight into the LSM tree, which can even be done on nodes that don't serve online traffic. For multi-tenant users with a very large number of tables, he said DDL for several tables can share a single schema version, and that for new tenants without statistics the optimizer can reuse a known-good set of plans. He also described the release they were then preparing, which uses an object store such as S3 as the back store: files are shipped through it rather than copied between nodes, compaction can run off to the side, and backups become mostly a metadata snapshot. The speaker presented this as reducing cost for customers. That is a vendor claim, so test it on your own workload.

The [TiDB DDL introduction](https://docs.pingcap.com/tidb/stable/ddl-introduction/) describes the same progression for adding an index: absent → delete only → write only → write reorg → public. That's how TiDB runs DDL online and asynchronously without blocking DML in other sessions.

**My take:** the part to remember is why "delete only" exists. In a rolling schema change, two adjacent states are live at the same time, and each state has to be safe next to the previous one. It is the same reasoning as an expand-and-contract migration in application code, applied inside the database.

### ClickHouse: pruning and HTTP errors

The evening finished with ClickHouse. A slide pointed to github.com/clickhouse/clickhouse and to the paper "ClickHouse - Lightning Fast Analytics for Everyone", and a closing slide listed three names. I can't match them to the two talks I filmed, so I'm describing the talks without names.

**Storage and pruning.** The first talk explained how ClickHouse stores data and avoids reading it. Every insert creates an immutable "part" on disk, sorted by the table's primary key, so an insert doesn't need to coordinate with existing data or check uniqueness. Background merges combine parts. It looks like an LSM tree, the speaker said, but there is no level hierarchy, so merges can be parallelised freely. Within a part, data is divided into **granules** of 8192 rows by default, and a small **sparse primary index** keeps the first row of each granule in memory. A query that filters on the key does a binary search on that index and loads only the matching granules. The speaker named two more pruning tools: **projections**, which are copies of the table sorted differently (at the cost of storage), and **skipping indexes** such as min-max and Bloom filters, which are cheaper but, in his words, harder to tune.

**HTTP errors in the middle of a stream.** The second talk was about a surprisingly practical problem. With chunked HTTP responses, ClickHouse may already have sent the `200` status when a query fails halfway through. A client that sees 200 assumes success. According to the speaker, the way the error was reported used to depend on the output format and on a setting, and clients in several languages had complained. A recent change, shipped in the 25.11 release, made it consistent: the old setting that wrote the exception into the output is now off by default, the exception block has a fixed size of 16 KB so a client knows how much to read, and the server deliberately breaks the chunked encoding by not sending the final empty chunk. That last point is the only way left to tell the client that the response is broken, and it's why `curl` exited with a non-zero code in his demo. He also showed the same failing query on an old and a new container, in CSV and JSON formats, with different results before and the same result after. My take: if you write an HTTP client for any streaming API, check what it does when the stream ends without the terminating chunk. Many clients treat a status code of 200 as the end of the story.

There was also a short, unscheduled talk after the ClickHouse slides about a write-ahead log and streaming engine written in Rust, which the speaker described as an alternative to Apache Kafka for single-node ingest. He had no slides and I didn't catch the project name reliably, so I'll leave it at that. For ClickHouse internals see my posts from the [ClickHouse Open House Amsterdam 2025](/blog/clickhouse-open-house-amsterdam-2025-picnic-langfuse/).

## What connects the two evenings

MVCC was the thread through both nights. On 26 November it came up as an operational problem: Bolt's slide on TiKV keeping too many versions for queue-like tables. On 4 December it was a correctness tool: the way PostgreSQL gives each transaction a consistent snapshot. Same mechanism, two very different costs. If you run a database at scale, you need to understand both.
